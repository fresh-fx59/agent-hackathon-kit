# SDD за 24 часа: сжатый цикл spec-driven development

Обычный SDD рассчитан на недели. На хакатоне он сжимается до одного часа
церемоний на весь день — но не исчезает: команды, которые «просто кодят»,
к утру не могут ответить, что именно они сдают и почему это хорошо.

## Цикл

```
Спека (30 мин) → План (30 мин) → Слайсы (строим) → Проверка каждого слайса
                                      ↑                    |
                                      └────────────────────┘
```

1. **Спека — 30 минут, не больше** (`spec-template.md`). Заполняется сразу
   после case-intake (`../docs/case-intake.md`). Таймер вслух. Всё, что не
   успели решить, — в «Открытые вопросы», а не в затягивание.
2. **План — 30 минут** (`plan-template.md`). Режем работу на **слайсы** —
   вертикальные куски, каждый из которых заканчивается ПРОВЕРЯЕМЫМ
   результатом («бенчмарк выдаёт число», а не «написан парсер»). Первый
   слайс — всегда пустой конвейер end-to-end (см. `../docs/strategy.md`).
3. **Задачи** (`tasks-template.md`) — живой чек-лист с владельцем и
   статусом. Обновляется по факту, а не «потом допишем». Это единственный
   документ, который редактируется весь день.
4. **Проверка каждого слайса**: `bash scripts/verify.sh` зелёный + прогон
   бенчмарка + коммит. Слайс без проверки не считается сделанным.

Спека и план после заполнения почти не меняются; если реальность разошлась
со спекой — правим спеку одной строкой (мини-decision log в конце), чтобы
в T+20 демо рассказывало ту же историю, что и документы.

## Когда церемонию можно пропустить

- **Правка меньше ~30 минут** (поправить вес в рубрике, переформулировать
  шаг skill.md) — без задачи в списке, просто коммит с внятным сообщением.
- **Прототип-разведка** («а сработает ли вообще X?») — таймбокс 1 час без
  документов; по итогам либо задача в план, либо выкидываем.
- **После feature freeze (T+16)** новые документы не пишутся вообще —
  только правки статусов задач.

## Когда церемонию пропускать НЕЛЬЗЯ

- Пропустить спеку целиком — нельзя: без критериев приёмки нечего мерить,
  а судят по бенчмарку.
- Начать второй слайс, пока первый не проверен, — нельзя: недоказанные
  слайсы копятся в несдаваемое болото.
- Менять цель кейса «на лету» без строки в decision log — нельзя: в 4 утра
  никто не вспомнит, почему свернули.

## Файлы

| Файл | Что это | Когда заполняется |
|---|---|---|
| `spec-template.md` | Спека: цель, объём, сценарии, критерии приёмки, риски | T+1, 30 минут |
| `plan-template.md` | План: слайсы с проверяемыми результатами | T+1.5, 30 минут |
| `tasks-template.md` | Чек-лист задач: владелец + статус | весь день, по факту |

Копируйте шаблоны в рабочий репозиторий кейса (например в `sdd/` рядом с
кодом) и заполняйте прямо в markdown — никакие трекеры для двоих на 24 часа
не нужны; трекер — это система записи для АГЕНТА, а не для вас.
