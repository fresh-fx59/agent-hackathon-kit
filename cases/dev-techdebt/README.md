# Кейс: детектор и фиксер техдолга (development)

Тренировочный кейс для трека «development»: агент находит технический долг в
небольшом сервисе управления заказами (`src/`, ~300 строк, 6 файлов) и
сравнивается с эталоном. В коде **намеренно** заложено 10 проблем: SQL-инъекция
через f-строку, голый `except`, изменяемый аргумент по умолчанию, мёртвый код,
дублированный блок в двух файлах, магические числа, сетевой запрос без
таймаута, захардкоженный ключ (заведомо фейковый `example-not-a-real-key`),
файл без контекстного менеджера.

Эталон — `expected-findings.json`. Смотреть его до прогона агента нельзя:
это ответы.

## Как прогнать кейс

1. **Поднять моки** (из корня репозитория):

   ```bash
   python3 mocks/run_all.py        # quality-мок слушает 127.0.0.1:8802
   ```

2. **Запустить агента** со скиллом `tracks/development/skill.md`. Агент обязан
   использовать ДВА источника: платформу качества через MCP
   (`mcp/quality_mcp.py`: `list_issues`, `get_measures`) и собственное чтение
   кода в `cases/dev-techdebt/src/`. Результат — `findings.json` по схеме из
   скилла.

3. **Посчитать метрику**:

   ```bash
   python3 cases/dev-techdebt/benchmark.py findings.json
   ```

   Совпадение = тот же файл + та же категория + строка в пределах ±5.
   Бенчмарк печатает precision / recall / F1, таблицу по категориям и списки
   пропущенных / лишних находок. ⚠️ Вывод раскрывает весь эталон
   (`expected-findings.json`) — если делаете ручной бейслайн «человек ищет
   долг сам», снимите его ДО первого запуска бенчмарка. Самопроверка бенчмарка:

   ```bash
   python3 cases/dev-techdebt/benchmark.py --self-test   # F1 = 1.0
   ```

## Продолжение (вторая половина кейса): фиксы через MR

После детекции агент предлагает исправления:

1. Для топ-N находок (начиная с severity `high`) агент готовит **минимальный
   диф** — только строки, относящиеся к находке, без попутного рефакторинга.
2. Каждый фикс оформляется **отдельным MR** через forge-мок
   (`mcp/forge_mcp.py`, инструмент `create_mr`, **проект `2` —
   `order-service`**, заведён в `mocks/forge/seed.json` именно под этот кейс):
   один MR = одна находка, в описании — категория, файл:строка и объяснение
   фикса.
3. Метрика хакатона: **% MR, принятых ревьюером без правок**. Считаем вручную:
   ревьюер (второй участник) смотрит каждый MR и отмечает
   «принят как есть / нужны правки / отклонён».

Правила безопасности фиксов — в скилле: сомневаешься в поведении → только
репорт без патча; никаких поведенческих изменений без теста.
