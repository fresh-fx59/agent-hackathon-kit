## Requirements

### R1 — Corpus and run identity at the input boundary

Record selected case, canonical corpus root, complete manifest, total files/records/bytes, configuration, intended and observed model identity, runtime version/hash and task prompt hash before investigation. The caller explicitly selects Winevtx. Reject a resolved root or manifest inconsistent with that selection; never fall back silently to another corpus. Resume must validate the same identity or create a new run with explicit provenance.

Do not embed Winevtx answers, maliciousness labels or expected timelines in the runtime. A manifest is identity evidence, not a truth oracle. Keep ground truth and review artifacts outside the model workspace. This scope gate prevents future dataset drift; current evidence does not establish that r3 itself mixed corpora or that the historical BlueSky launch was automatic fallback.

### R2 — Field extraction with provenance and unknown states

Extend the existing readers with a versioned Windows-export adapter, retaining the generic reader. Support scalar/dictionary EventID, EventData objects/lists and UserData nested records. Preserve original value, parsed value, JSON pointer, corpus-relative file, physical line, provider/channel/event/version and timestamp precision. Duplicate named fields remain distinguishable; ambiguous or malformed data is surfaced, never silently coerced to zero or success.

Missing, empty, unparsable, unsupported and present values must remain distinct. Provider-specific meanings require qualified metadata and tests. Unknown event semantics retain raw values. Microsoft XML documentation is not a JSON-export schema: actual exporter variants must be tested directly.

### R3 — Exhaustive evidence calculations

Build on `logmap` rather than replace it. A partition operation returns predicate, scope, denominator, every outcome bucket, unknown/malformed counts and representative exact references. Bucket totals must reconcile with the scanned population. Material minority outcomes cannot disappear behind top-N summaries. Large result sets use complete pagination or streamed artifacts with continuation/completion receipts; no oldest/newest fixed-window cap.

Counts must declare their unit: events, unique entities, sessions, rules, or reconstructed state. Distinct counts require a stated identity key. Effective policy claims require a complete supported state reconstruction; otherwise report only observed events/configuration. Full bucket evidence can remain in artifacts; the report summarizes material exceptions without printing every row.

Build on `logjoin` for chronology and correlation. Compute min/max and deltas from parsed UTC timestamps, not physical line order. Preserve precision and invalid timestamp counts. Join receipts declare keys, time window, direction, tie handling, reused matches, unmatched records and one-to-many ambiguity. Never turn proximity into causal or one-to-one proof.

### R4 — Narrowly defined material-claim evidence

Introduce a versioned sidecar for material quantitative, chronological, universal-negative, identity/configuration and cross-source claims. Suggested record:

```json
{
  "schema_version": 1,
  "claim_id": "c17",
  "report_anchor": "finding-3",
  "kind": "partition",
  "scope_ref": "scope-2",
  "operation_ref": "operation-9",
  "result_ref": "result-9",
  "source_refs": [{"file": "channel.jsonl", "line": 42, "pointer": "/Event/EventData/Code"}],
  "qualification": "Observed outcome; intent unknown"
}
```

This is a proposed contract, not implemented API. Operation parameters and results must be serialized, content-addressed and replayable with deterministic tools, not executable model-generated shell strings. Claims bind to a corpus manifest and final report digest; edits invalidate the final validation receipt.

Scope includes channel/provider/event population, time bounds, predicates, parse failures, scan completion and coverage gaps. A negative can mean only “no matching evidence in this declared scope”; missing channels or unsupported fields cannot produce an exhaustive negative. Material identity claims distinguish subject, target, session user, service logon identity, process context and human actor. Configuration does not become observed execution.

Reuse validated fact values when rendering structured findings/tables. Mechanical checks verify exact supported values and references within those blocks. Free prose still needs semantic review: a well-formed sidecar cannot prove that all nearby prose follows from evidence. Avoid promises of automatic general entailment or zero future hallucinations.

### R5 — Completion checks must execute and report their real result

The post-r3 runner commit `73c1c8f36a17c4ebaa55791b02ef86b723892112` already exports the hook skill root. Verify that repair through the actual hook before adding another fix; it does not retroactively validate r3. Fix or confirm runtime-root resolution using the installed script/package location, with explicit environment override validation. Missing root, missing check, nonzero check, crash, timeout or malformed response must produce an identifiable infrastructure/check failure. Preserve diagnostics and the draft report; do not label an unvalidated report PASS.

Test the actual Qwen completion-hook invocation with the environment absent, not just direct Python calls. Determine the host's supported retry/stop behavior from a local integration fixture. A terminal receipt records which checks ran, their input hashes, status and final report hash. Separate process exit, artifact existence, structural validation and source/semantic acceptance.

Compose existing stop/state/report/citation/worklist checks with the new deterministic claim checks. An absent sidecar for required claim types is a contract failure. Do not introduce a production LLM judge or an unconditional external-network dependency.

### R6 — Reusable semantic references

Ship only verified, provider/version-qualified mappings needed by the adapter, with source URL or metadata provenance and explicit unknown fallback. Preserve raw numbers alongside decoded labels. Review firewall direction/action mapping, logon type, and session lifecycle semantics independently. A global dictionary keyed only by EventID or a field name is forbidden.

Microsoft primary references support schema, 4625 and firewall enum interpretation. This research did not establish authoritative standalone 5379 or LSM tables. Obtain official provider metadata/message resources or a reproducible version-qualified Windows export before including those mappings. Until then, keep raw fields and narrowly stated corpus observations.

Development fixtures must be small synthetic cases with changed names, dates, frequencies and payload order. Winevtx facts stay in evaluator fixtures only. Preserve generic non-Windows tests so specialization does not break the broader tool contract.

For final target assessment, evaluate the untouched report against the full corpus with deterministic claim replay and an independent semantic review. Require every material discrepancy listed above to be resolved or explicitly qualified, no new material unsupported claims, accurate citations, real completion-check receipts and case identity. Run at least three fresh target trials under the same frozen configuration before claiming repeatability; report pass count and all failures, not only the best report. Three passes support that limited observation, not a universal reliability claim. Target trials consume the configured provider budget and belong to implementation/evaluation, not this specification task.

## Primary research and its limits

These recommendations are engineering inferences from observed failures and guidance, not a certification by any source.

- [Microsoft EventType schema](https://learn.microsoft.com/en-us/windows/win32/wes/eventschema-eventtype-complextype): preserve payload structure and distinguish system metadata from event-specific fields.
- [Microsoft 4625](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4625): type3 denotes network logon; account roles and authentication fields have separate meanings.
- [Windows PowerShell 5.1 event logs](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_eventlogs?view=powershell-5.1): classic engine/provider logging is distinct from script-block evidence.
- [Microsoft FW_RULE_ACTION](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fasp/702e3c23-c9d8-43db-8380-b4c670dd7f7d): use documented enums within their qualified schema.
- [NIST SP 800-86, sections3.2–3.4](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-86.pdf): preserve methods, separate examination from analysis/reporting, correlate sources and consider alternatives.
- [NIST SP 800-61r3, April2025](https://csrc.nist.gov/pubs/sp/800/61/r3/final): incident analysis should support response decisions within risk management.
- [Anthropic, Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents): distinguish transcript from outcome and use complementary graders and repeated trials.
