# Installed Qwen nested-agent lifecycle capture — r1/r2/r3/r4b

Both captures used installed Qwen 0.22.0 as `claude-developer`, an isolated HOME/workspace, and a localhost scripted SSE endpoint. No real provider, credential, Sherlock runtime, or production source was used.

Installed source `chunk-T6XLJRQY.js:70541-70545` creates an agent identifier as the resolved subagent name plus the parent provider call ID. `:115157-115173` emits SubagentStart with `agent_id` and `agent_type`; it does not supply parent tool ID. The r1 capture confirms the exact relation: parent `call_parent_agent` produces `mock-triage-call_parent_agent`.

r1 (`/tmp/qwen-nested-agent-capture-20260906-r1/evidence`) made three requests. Hook order was UserPromptSubmit, parent PreToolUse, SubagentStart, child request, SubagentStop, parent PostToolUse, outer PostToolBatch, UserPromptSubmit, then parent continuation. The child HTTP request has no session, prompt, parent, agent ID, or agent type metadata; it has the same generic Qwen user-agent and ordinary chat-completions body shape.

r2 (`/tmp/qwen-nested-agent-capture-20260906-r2/evidence`) made the child execute a shell tool. It proves the nested ordering: parent PreToolUse → SubagentStart → child PreToolUse/PostToolUse → inner PostToolBatch → SubagentStop → parent PostToolUse → outer PostToolBatch. Child tool hooks carry the same root session and no agent ID/type. UserPromptSubmit appears only at the root turn boundaries, not before the child request.

This establishes that a proxy cannot safely authorize child traffic from HTTP metadata or a global pending-parent flag. The available narrow authority is a pending parent `agent` provider call plus a matching SubagentStart exact `agent_id = resolved_agent_type + '-' + parent_call_id`, with nested tool and batch accounting completed before the matching SubagentStop and parent pair are accepted.
