# Кейс «аналитика»: стенограмма встречи → BR → задача в корпоративном трекере

Тренировочный кейс для трека аналитики: агент читает русскоязычную стенограмму
встречи, извлекает требования, оформляет документ бизнес-требований (BR) по
шаблону и заводит задачу типа `BR` в корпоративном трекере через MCP.

## Файлы кейса

| Файл | Что это |
|------|---------|
| `transcript-ru.md` | Входные данные: стенограмма встречи про заявки на командировки (с противоречиями, которые разрешаются по ходу встречи, и с болтовнёй-шумом). |
| `rubric.json` | Рубрика оценки: обязательные разделы BR + 12 обязательных фактов с ключевыми словами и весами. |
| `expected-br.md` | Эталонный BR («золотой» ответ) — как должен выглядеть результат. |
| `benchmark.py` | Скоринг BR по рубрике: 0–100, таблица покрытия, список пропущенных фактов. |

## Как прогнать кейс целиком

1. **Поднять мок трекера** (из корня репозитория):

   ```bash
   python3 mocks/tracker/app.py          # 127.0.0.1:8801
   # или все моки сразу: python3 mocks/run_all.py
   ```

2. **Подключить MCP-сервер трекера** к вашему агенту/CLI (конфиг в стиле
   `mcpServers`, см. `mcp/configs/`):

   ```json
   {"tracker": {"command": "python3", "args": ["mcp/tracker_mcp.py"]}}
   ```

3. **Запустить агента с навыком** `tracks/analytics/skill.md`, подав на вход
   `cases/analytics-meeting/transcript-ru.md`. Агент должен:
   - написать BR (например, в `br-agent.md`) строго по шаблону
     `tracks/analytics/templates/br-template-ru.md`;
   - создать задачу через MCP-инструмент `create_issue`
     (type=`BR`, `meeting_ref="meet-2026-07-27-trips"`).

4. **Оценить результат** бенчмарком:

   ```bash
   python3 cases/analytics-meeting/benchmark.py br-agent.md
   ```

   Скор 0–100: 30% — наличие всех разделов шаблона, 70% — покрытие фактов
   из рубрики (взвешенное). Пропущенные факты печатаются списком — это готовый
   план доработки промпта/навыка.

5. **Проверить задачу в трекере** (через MCP `get_issue` или напрямую):

   ```bash
   curl -s -H 'User-Agent: agent-hackathon-kit/0.1' http://127.0.0.1:8801/issues?type=BR
   ```

## Самопроверка рубрики

```bash
python3 cases/analytics-meeting/benchmark.py --self-test
```

Скорит эталонный `expected-br.md`; должно быть ≥ 95 (сейчас 100). Если после
правок рубрики или эталона самопроверка падает — сначала чините их согласованность.

## На что смотреть в оценке

- **Противоречия**: на встрече значения менялись (порог 100 000 → 150 000 руб.,
  срок 5 → 3 рабочих дня, маршрут согласования расширился). Правильный BR
  содержит **финальные** значения — рубрика проверяет именно их.
- **Шум**: кофе, проблемы со звуком, шутки про принтер и отпуск в BR попадать
  не должны.
- **Открытые вопросы**: режим выгрузки в бухгалтерию и мобильная версия на
  встрече НЕ решены — в BR они должны быть в «Открытых вопросах», а не в
  требованиях.

## Ручной бейслайн (для демо «агент vs человек»)

Чтобы на демо показать выигрыш, зафиксируйте время ручной работы:

1. Один участник команды **до** запуска агента садится с `transcript-ru.md`
   и пишет BR руками по тому же шаблону, с таймером (обычно 30–60 минут).
   ⚠️ Бенчмарк печатает полную эталонную таблицу фактов — «ручной» участник
   не должен запускать `benchmark.py` (и открывать `expected-br.md`/`rubric.json`)
   до того, как закончит свой BR, иначе бейслайн испорчен подсказками.
2. Запишите: время, скор его BR по `benchmark.py`, время агента и скор агента.
3. Результат — табличка «человек: N минут / X баллов, агент: M минут / Y баллов»
   в демо-слайд.

Важно: человек и агент работают с одной и той же стенограммой и одним шаблоном —
иначе сравнение нечестное.
