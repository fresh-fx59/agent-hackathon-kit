# Скилл: умная регрессия по диффу MR (трек testing)

Ты — агент-тестировщик. По диффу merge request'а ты выбираешь МИНИМАЛЬНО
ДОСТАТОЧНЫЙ набор регрессионных тест-кейсов из карты покрытия TMS, выдаёшь
`selection.json` с обоснованием по каждому кейсу и заводишь прогон в TMS.
Главный принцип: **пропущенный дефект дороже лишнего теста** — при сомнении
включай кейс.

## Входы

- MCP-сервер репозитория `forge` (`mcp/forge_mcp.py`, GitLab-подобный):
  - `get_mr(project_id, iid)` — сводка MR (ветки, описание, changes_count);
  - `get_mr_diff(project_id, iid)` — изменённые файлы с unified-диффами;
  - `get_file(project_id, path)` — текущее содержимое файла (для анализа
    импортов и вызовов);
  - `create_mr(...)` — здесь не нужен (пригодится в треке development).
- MCP-сервер тест-менеджмента `tms` (`mcp/tms_mcp.py`):
  - `list_testcases(area?)` — карта кейсов: `id, title, area, priority,
    files_covered, tags, last_result, avg_duration_min`;
  - `create_run(case_ids, reason)` — завести прогон из выбранных кейсов.
- Номер MR (в тренировочном кейсе — проект `1`, MR `1`).

## Процедура

1. **Сними дифф.** `get_mr` + `get_mr_diff`. Выпиши список изменённых файлов
   (`new_path`) и по хвостам диффа пойми, ЧТО именно поменялось (константы,
   условия, новые проверки) — это нужно для обоснований.
2. **Сними карту кейсов.** `list_testcases` без фильтра. Построй индекс:
   файл → кейсы, у которых он в `files_covered`.
3. **Прямое покрытие.** Кейс, у которого в `files_covered` есть изменённый
   файл, идёт в выборку безусловно — включая e2e-кейсы, где изменённый файл
   лишь один из нескольких.
4. **Транзитивное покрытие.** Изменение утекает за пределы изменённого файла
   двумя путями; проверь оба:
   - **импорты/вызовы:** через `get_file` посмотри, кто импортирует
     изменённые модули и чьё поведение зависит от их выходов (например,
     письмо-подтверждение строится из заказа, который считает checkout);
   - **данные:** если дифф начинает использовать новые данные (например,
     остатки склада из каталога) — кейсы вокруг этих данных попадают в зону
     риска.
   Такие кейсы включай с пометкой транзитивности в `reason`.
5. **Ранжируй по риску: приоритет × покрытие.** P1-кейс с прямым покрытием —
   всегда в выборке; P2/P3 с прямым покрытием — в выборке (это регрессия
   изменённого кода, отказываться можно только при явном лимите времени, и
   отказ фиксируй в `strategy`); транзитивные P2/P3 — в выборку или в явный
   осознанный отказ. Упавшие/заблокированные в прошлом прогоне
   (`last_result != passed`) кейсы из зоны изменений — обязательны:
   там уже неспокойно.
6. **Всегда добавляй P1-смоук.** Все кейсы с приоритетом P1 и тегом `smoke`
   включаются даже вне зоны изменений — это страховка от неожиданных связей.
7. **Собери `selection.json`** (контракт ниже): у КАЖДОГО кейса — конкретная
   причина («изменён app/cart.py: лимит позиции 99 → 20», а не «связан с
   корзиной»). В `strategy` — 2–4 предложения: какие файлы изменены, как
   считалось транзитивное покрытие, от чего отказался и почему.
8. **Заведи прогон:** `create_run(case_ids=<выбранные id>, reason=<MR и суть
   изменений>)`. Приложи `run_id` к ответу.

## Контракт выхода: selection.json

```json
{
  "selected": [
    {"id": "TC-5", "reason": "app/cart.py: лимит позиции снижен 99 → 20 — граничный кейс"}
  ],
  "strategy": "Изменены app/cart.py (валидация количества, проверка остатков) и app/checkout.py (модель скидок best-of). Прямое покрытие по files_covered + транзитивное через e2e-потоки и письмо-подтверждение. P1-смоук включён полностью."
}
```

Только эти поля. `id` — строго из карты кейсов; один кейс — один раз.

## Чек-лист качества (перед сдачей)

- [ ] Каждый изменённый файл из диффа разобран: список кейсов с ним в
      `files_covered` выписан полностью, ни один не потерян.
- [ ] Транзитивные зависимости проверены по коду (`get_file`), а не по
      догадке.
- [ ] Все P1 из зоны изменений и весь P1-смоук — в выборке.
- [ ] У каждого кейса конкретный `reason` со ссылкой на файл/суть изменения.
- [ ] Нет дублей `id`; все `id` существуют в карте.
- [ ] Прогон заведён через `create_run`, `run_id` получен.
- [ ] **Сомневаешься — включай:** recall важнее efficiency; лишний тест
      стоит минуты, пропущенный дефект — релиза.
- [ ] Прогнан бенчмарк: `python3 cases/testing-regression/benchmark.py
      selection.json` (recall должен быть 1.00).

## Режимы отказа (что делать, когда что-то не так)

- **Дифф недоступен** (`get_mr_diff` вернул ошибку) → не гадай по названию
  MR; сообщи об отказе источника и предложи полную регрессию (все кейсы) как
  безопасный fallback.
- **Карта кейсов пуста или без `files_covered`** → выбор по файлам невозможен;
  отбирай по `area`+`priority` (все области, которых касается описание MR,
  плюс P1-смоук) и явно пометь в `strategy`, что маппинг по файлам выпал.
- **Дифф огромный** (десятки файлов) → не расширяй выборку до «почти всё»
  молча: сгруппируй файлы по областям, покажи расчёт и предложи полную
  регрессию, если выборка превысила ~70% карты.
- **Изменённый файл не встречается ни в одном `files_covered`** → это дыра в
  карте покрытия, а не повод пропустить: включи ближайшие по области/потоку
  кейсы и явно отметь дыру в `strategy`.
- **TMS недоступен для `create_run`** → всё равно выдай `selection.json`
  (он самоценен), а команду на создание прогона приложи текстом для ручного
  повтора.
