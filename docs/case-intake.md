# Case intake: рабочий лист первых 60 минут

Заполняется СРАЗУ после объявления кейса, вдвоём, прямо в этом файле
(скопируйте его в `sdd/` рабочего репозитория). Цель — за час превратить
текст кейса в план, где каждый ответ указывает на конкретный файл kit.

Правило: **не начинать писать код, пока лист не заполнен.** Полчаса
заполнения экономят четыре часа переделок.

## Заполненный пример: кейс «встреча → BR»

### 1. Вход
- Транскрипт встречи с заказчиком, RU, markdown-файл ~6 страниц
  (образец: `cases/analytics-meeting/transcript-ru.md`).
- Объём < 30k токенов — влезает в контекст целиком, чанкование не нужно.

### 2. Артефакт-результат
- Документ BR на русском по шаблону
  `tracks/analytics/templates/br-template-ru.md`: Цель, Контекст,
  Заинтересованные стороны, ФТ-1…, НФТ, Критерии приёмки, Ограничения,
  Открытые вопросы, Следующие шаги.
- Потребитель — судья (сверка с рубрикой) и трекер (задача со ссылкой на BR).

### 3. Система записи
- Корпоративный трекер (Jira-подобный). Аналог в kit: `mocks/tracker/`
  (порт 8801) + `mcp/tracker_mcp.py` (tools: `create_issue`, `list_issues`,
  `get_issue`, `update_issue`).
- В корпоративной среде: заменить `TRACKER_URL` на реальный API, добавить
  auth-заголовок (см. `transfer.md`).

### 4. Core-агент
- Аналитик-агент умеет диалог и чтение файлов; не умеет наш формат BR и не
  имеет доступа к трекеру.
- Наша работа: skill.md (`tracks/analytics/skill.md` → адаптировать),
  MCP-конфиг на `tracker_mcp.py`, прогнанный пример.

### 5. Бенчмарк
- Метрика: покрытие рубрики 0–100 (`cases/analytics-meeting/benchmark.py`
  против `rubric.json`: обязательные секции + взвешенные факты).
- Ручной baseline: кейс-owner пишет BR руками по тому же транскрипту,
  T+1…T+3, фиксируем минуты и балл. Эталон — `expected-br.md`.

### 6. Копируем
- [x] `mocks/tracker/`, [x] `mcp/tracker_mcp.py`,
- [x] `tracks/analytics/skill.md`, [x] `tracks/analytics/templates/br-template-ru.md`,
- [x] `cases/analytics-meeting/benchmark.py` + `rubric.json` (правим факты под
  реальную встречу), [x] `sdd/spec-template.md`.

### 7. Риски
1. Транскрипт длиннее ожидаемого → чанкование по говорящим/темам
   (`transfer.md`), сборка BR по частям.
2. Формат skill.md core-агента отличается → наш skill.md — чистый markdown,
   переносим содержимое в их обёртку.
3. Рубрика организаторов не совпадает с нашей → `benchmark.py` принимает
   рубрику файлом — подменяем `rubric.json`, код не трогаем.
