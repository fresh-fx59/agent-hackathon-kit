# Стратегия: как выиграть 24-часовой PDLC-хакатон вдвоём

Принцип всей стратегии: **судьи сравнивают числа, а не архитектуры.**
Побеждает команда, которая раньше всех получает измеримый результат и весь
остаток времени двигает метрику вверх, показывая это в понятном демо.

## Выбор трека: первые 30 минут

Не выбирайте трек «по интересности». Прогоните все три через три фильтра
и посчитайте очки (1–3 по каждому фильтру, максимум 9):

**1. Совпадение с навыками команды.**
- Аналитика = работа с текстом на русском, структурирование, шаблоны
  документов. Минимум кода.
- Разработка = чтение чужого кода, статический анализ, авто-фиксы. Больше
  всего инженерии и больше всего способов закопаться.
- Тестирование = рассуждение о зависимостях (дифф → задетые файлы → тесты).
  Самый алгоритмизируемый и самый предсказуемый по объёму.

**2. Измеримость бенчмарка.** Сможете ли вы за первый час получить ЧИСЛО?
- Тестирование: recall/efficiency считаются скриптом мгновенно — отлично.
- Разработка: F1 против эталона — хорошо, если эталон дают; иначе строить
  свой (полдня).
- Аналитика: качество BR субъективнее; спасает рубрика (обязательные секции +
  факты) — как в `cases/analytics-meeting/rubric.json`.

**3. Демонстрируемость.** Что судья увидит за 3 минуты?
- Живой MCP-вызов «агент создал задачу в трекере» — зрелищно (аналитика).
- Таблица «нашли 14/16 проблем, анализатор класса SonarQube — 9» — убедительно
  (разработка).
- «Гоняем 6 тестов вместо 25, ни один дефект не упущен» — мгновенно понятно
  (тестирование).

Решение фиксируйте до конца первого получаса и **не пересматривайте** —
смена трека после T+4 почти гарантированно означает несданное демо.

## Общая форма кейса — стройте конвейер, а не фичи

Все известные кейсы (и, скорее всего, реальный) устроены одинаково:

```
вход (транскрипт / код / дифф)
  → анализ по skill.md
  → структурированный артефакт (markdown или JSON по схеме)
  → запись в систему через MCP
  → бенчмарк против ручного baseline
```

Практическое следствие: **сначала прогоните пустой конвейер end-to-end**
(вход → тривиальный артефакт → MCP-запись → бенчмарк выдал число, пусть
низкое), и только потом улучшайте качество анализа. Конвейер, дающий 40
баллов в T+4, ценнее идеального анализатора, не доехавшего до MCP к T+20.

## Бенчмарк — прежде всего

1. **Ручной baseline снимайте РАНО** (до T+3). Один человек руками решает
   кейс на фрагменте входа и засекает время и качество. Это даёт:
   - строку «человек: 45 минут, 78 баллов» для финальной таблицы;
   - эталон для отладки агента;
   - глубокое понимание кейса (самый недооценённый эффект).
2. **Скрипт скоринга — это продукт.** Судьи любят, когда команда принесла
   свой воспроизводимый `benchmark.py` c `--self-test`. Берите за основу
   любой из `cases/*/benchmark.py`.
3. **Каждый прогон — в таблицу.** Простая история «14:00 — 42 балла,
   18:00 — 71, 23:00 — 89» на слайде демо показывает инженерный процесс
   лучше любых слов.

## Демо: 3 минуты, которые решают всё

- **Структура:** 20 сек — кейс своими словами; 60 сек — живой прогон;
  60 сек — бенчмарк-таблица; 40 сек — что бы сделали дальше.
- **Покажите MCP-вызов вживую:** терминал, агент думает, и в соседнем окне
  в трекере появляется задача / в TMS — прогон. Это «вау-момент» — отрепетируйте
  его отдельно не меньше трёх раз.
- **Таблица бенчмарка — главный слайд.** Агент vs ручной baseline vs (если
  есть) статический анализатор. Числа крупно.
- **Запишите резервный прогон заранее** (запись экрана в T+20, пока всё
  зелёное). Если на демо упадёт Wi-Fi, мок или модель — включаете запись и
  спокойно комментируете. Команды без записи в этот момент умирают на сцене.
- Один человек говорит, второй за клавиатурой. Прогоните вслух дважды.

## Анти-паттерны (проверено чужими провалами)

- Писать свой «более умный core-агент» — его уже написали организаторы,
  очки дают за обвязку и результат на кейсе.
- Улучшать анализ до того, как конвейер доехал до MCP-записи и бенчмарка.
- Полировать промпт без скрипта скоринга — «стало вроде лучше» не аргумент.
- Тянуть внешние зависимости: одна сломанная установка пакета в закрытой
  среде съедает час. Всё в kit работает на stdlib — держите эту планку.
- Демо «с листа» без резервной записи.
