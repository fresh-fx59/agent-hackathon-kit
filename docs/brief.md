# Бриф: что мы знаем о хакатоне

Собранные факты о формате, три известных примерных кейса и честная таблица
«знаем / не знаем / предполагаем». Всё, что помечено как предположение,
проверяем в первые 30 минут хакатона (см. `case-intake.md`).

## Формат

- **24 часа**, команда из 2 человек, корпоративный хакатон Компании.
- Треки соответствуют этапам **PDLC**: **аналитика / разработка / тестирование**.
- У организаторов уже есть **готовые «core-агенты»** по каждому треку —
  участники их не пишут. Задача команды — сделать агента полезным на реальном
  кейсе, то есть поставить вокруг него обвязку:
  - **MCP-инструменты** (доступ агента к корпоративным системам),
  - **skill.md** (инструкция-навык: как агент решает кейс),
  - **необходимые компоненты** (парсеры, шаблоны артефактов, glue-код),
  - **примеры** (прогнанные end-to-end образцы).
- **Кейсы объявляют на старте** — до этого известны только примеры (ниже).
- **Судейство по бенчмаркам**: результат агента сравнивают с ручным
  базовым уровнем (baseline) и/или эталоном. Числа решают.
- Корпоративная среда: CLI-агент класса qwen-coder с моделью класса
  DeepSeek (контекст 256k), поддержка MCP (клиент и сервер), skills,
  субагентов и SDD; Jenkins; git-платформа класса GitLab; Pixso;
  боты в корпоративном мессенджере; выданные вручную ВМ.
- Среда **может пулить публичный GitHub, но пуш наружу запрещён** —
  поэтому весь kit одноходово переносится `git clone` и работает на голом
  `python3` (stdlib-only).

## Три известных примерных кейса

### 1. Аналитика: встреча → бизнес-требования (BR)

- **Вход:** запись/транскрипт встречи с заказчиком (RU).
- **Работа агента:** извлечь цели, требования, ограничения, открытые вопросы;
  оформить структурированный документ BR; **создать задачу в корпоративном
  трекере** через MCP.
- **Бенчмарк:** полнота и точность BR против ручного разбора той же встречи —
  покрытие обязательных секций и фактов (в kit: `cases/analytics-meeting/`,
  `rubric.json` + `benchmark.py`, счёт 0–100).

### 2. Разработка: детектор и фиксер техдолга

- **Вход:** кодовая база с накопленным техдолгом.
- **Работа агента:** найти проблемы (безопасность, баги, smells, дубли,
  мёртвый код), классифицировать, предложить/применить исправления;
  сверяться с анализатором качества класса SonarQube через MCP.
- **Бенчмарк:** precision / recall / F1 найденных проблем против эталонного
  списка; базовый уровень — отчёт статического анализатора (в kit:
  `cases/dev-techdebt/`, `expected-findings.json` + `benchmark.py`).

### 3. Тестирование: умная регрессия по диффу PR

- **Вход:** дифф merge-request'а + карта покрытия «тест-кейс → файлы».
- **Работа агента:** выбрать минимальный достаточный набор регрессионных
  тестов, объяснить выбор, создать прогон в TMS через MCP.
- **Бенчмарк:** recall по обязательным кейсам (цель 1.0) + эффективность
  (насколько меньше полного прогона) против ручного выбора тест-лида
  (в kit: `cases/testing-regression/`, `expected-selection.json` +
  `benchmark.py`).

## Общая форма всех кейсов

```
неструктурированный вход (транскрипт / код / дифф)
  → анализ по skill.md
  → структурированный артефакт (BR / findings.json / selection.json)
  → запись в корпоративную систему через MCP (трекер / MR / прогон в TMS)
  → бенчмарк против ручного базового уровня
```

Именно эту форму kit покрывает целиком: моки систем (`mocks/`), MCP-серверы
(`mcp/`), скиллы (`tracks/`), артефакты и скоринг (`cases/`).

## Знаем / не знаем / предполагаем

| Вопрос | Статус | Детали / план проверки |
|---|---|---|
| Длительность 24 часа, команда 2 человека | **Знаем** | — |
| Треки = аналитика / разработка / тестирование (PDLC) | **Знаем** | — |
| Core-агенты уже есть, команды пишут MCP + skill.md + компоненты + примеры | **Знаем** | На старте: прочитать интерфейс core-агента (как он грузит skills и MCP-конфиг) |
| Кейсы объявляют на старте | **Знаем** | Первые 60 минут — по `case-intake.md` |
| Судейство по бенчмаркам против ручного baseline | **Знаем** | Уточнить на старте: кто меряет, чем, какая метрика главная |
| CLI-агент класса qwen-coder, модель класса DeepSeek, 256k контекста | **Знаем** | Советы по промптингу — `transfer.md` |
| MCP клиент+сервер, skills, субагенты, SDD поддерживаются | **Знаем** | Формат конфига MCP уточнить на месте (`mcp/configs/README.md` — генерные варианты) |
| GitHub pull разрешён, push наружу запрещён | **Знаем** | Перенос — только clone/pull, см. `transfer.md` |
| Точный формат skill.md, который ест core-агент | **Не знаем** | На старте открыть пример организаторов; наши `tracks/*/skill.md` держим в переносимом markdown |
| Какие именно корпоративные системы доступны и их API | **Не знаем** | Моки повторяют жанры (Jira-/Sonar-/GitLab-подобные, TMS); адаптация = URL + auth-заголовок |
| Формат объявления кейса (текст? репозиторий? данные?) | **Не знаем** | Worksheet в `case-intake.md` работает с любым входом |
| Есть ли интернет из среды кроме GitHub-pull | **Не знаем** | Считаем что нет: kit самодостаточен |
| Разрешена ли внешняя AI-помощь во время хакатона | **Не знаем** | **Проверить правила до старта** |
| Кейс будет вариацией одного из трёх примеров | **Предполагаем** | Если нет — общая форма (вход → артефакт → MCP → бенчмарк) всё равно применима |
| Судьи дадут доступ к baseline-числам | **Предполагаем** | Если нет — меряем ручной baseline сами и показываем таблицу (см. `strategy.md`) |
| На ВМ есть python3 ≥ 3.9 | **Предполагаем** | `scripts/bootstrap.sh` проверяет за 5 секунд |

## Чек-лист артефактов, которые ждут от команды

- [ ] MCP-сервер(ы), подключённые к core-агенту, с работающими tools.
- [ ] skill.md по выбранному треку, адаптированный под кейс.
- [ ] Структурированный артефакт-результат (BR / findings / selection) по схеме.
- [ ] Прогнанный end-to-end пример: вход → артефакт → запись через MCP.
- [ ] Бенчмарк-таблица: агент vs ручной baseline, с числами.
- [ ] Демо (живое + резервная запись — см. `strategy.md`).
