# Промпт: развернуть кит и настроить CI-гейт силами корпоративного агента

Этот файл — **готовый промпт**. Скопируйте всё, что ниже разделительной
черты, целиком в корпоративный CLI-агент (у команды это qwen-coder-подобный
CLI с DeepSeek-класс моделью — точное название подставьте сами) и отправьте.
Агент развернёт кит и настроит CI-гейт по шагам, отчитываясь после каждого.

Перед отправкой при необходимости замените:

- `<URL_КИТА>` → адрес репозитория, доступный из корпоративной среды
  (публичный GitHub: `https://github.com/fresh-fx59/agent-hackathon-kit.git`,
  либо внутреннее зеркало);
- `<КАТАЛОГ>` → рабочий каталог, куда клонировать (например, `~/hack`).

---

Ты — агент в корпоративной среде компании. Твоя задача — развернуть набор
agent-hackathon-kit и настроить CI-гейт. Выполняй шаги по порядку, после
каждого шага сообщай результат: что сделал, что получилось, что не
получилось и почему. Не переходи к следующему шагу, пока текущий не
завершён или не зафиксирован как заблокированный.

## Шаг 1. Получить код кита

1. Если каталог `<КАТАЛОГ>/agent-hackathon-kit` ещё не существует:
   `git clone <URL_КИТА> <КАТАЛОГ>/agent-hackathon-kit`.
2. Если уже существует: `cd <КАТАЛОГ>/agent-hackathon-kit && git pull`.
3. Среда — pull-only: наружу пушить нельзя и не потребуется. Все локальные
   правки (конфиги, артефакты) остаются локальными; ничего не коммить
   в этот репозиторий.
4. Доложи: команду, которой получил код, и текущий коммит (`git log -1 --oneline`).

## Шаг 2. Проверить окружение и прогнать самопроверку

1. `cd <КАТАЛОГ>/agent-hackathon-kit`
2. `bash scripts/bootstrap.sh` — должен напечатать `OK` про версию Python.
3. `bash scripts/verify.sh` — в конце должно быть `RESULT: PASS`.
4. Если `python3` нет или он старше 3.9:
   - поищи другой бинарь: `command -v python3.9 python3.10 python3.11 python3.12`;
     если нашёлся — используй его явно (`python3.11 mocks/run_all.py` и т.д.)
     или добавь алиас/симлинк в свой PATH;
   - если ничего нет — поставь Python ≥ 3.9 из корпоративного зеркала
     пакетов (кит stdlib-only: pip, venv и внешние пакеты НЕ нужны, достаточно
     самого интерпретатора);
   - если установка недоступна — остановись и доложи оператору: без
     python3 ≥ 3.9 кит не работает.
5. Доложи: вывод версии Python и последнюю строку `verify.sh`
   (`RESULT: PASS` / `RESULT: FAIL` + какие пункты упали).

## Шаг 3. Зарегистрировать 4 MCP-сервера в своём CLI

1. Эталонная конфигурация — `mcp/configs/all-servers.json`: четыре stdio-сервера
   (`tracker`, `quality`, `forge`, `tms`), каждый запускается как
   `python3 mcp/<имя>_mcp.py` с env-переменной `*_URL`, указывающей на мок
   (`http://127.0.0.1:8801..8804`).
2. Перенеси эти четыре записи в **родной формат конфигурации своего CLI**
   (у большинства агентских CLI это файл/секция вида `mcpServers`; примеры
   разных форм — в `mcp/configs/README.md` и `docs/mcp-cheatsheet.md`).
   Пути к `mcp/*_mcp.py` указывай абсолютные, чтобы не зависеть от cwd.
3. Проверь каждый сервер сырым пайпом (initialize + tools/list), не полагаясь
   на CLI:

   ```sh
   printf '%s\n%s\n' \
     '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' \
     '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' | python3 mcp/tracker_mcp.py
   ```

   В ответе на `id:2` должен быть непустой список `tools`. Повтори для всех
   четырёх серверов.
4. Затем проверь через сам CLI: запусти моки (`python3 mocks/run_all.py`),
   попроси себя же вызвать `list_issues` у сервера `tracker` — должны
   вернуться сидовые задачи `TRK-1..TRK-3`.
5. Доложи: где лежит твой конфиг, сколько инструментов отдал каждый сервер.

## Шаг 4. Настроить CI-гейт

Вариант А — **есть Jenkins**:

1. Создай Pipeline-job: «Pipeline script from SCM», репозиторий кита,
   Script Path = `ci/Jenkinsfile`.
2. Параметры уже объявлены в Jenkinsfile: `CASE_DIR`
   (по умолчанию `cases/analytics-meeting`), `MIN_SCORE` (`80`), `ARTIFACT`
   (пусто = гейт только по самопроверке харнесса).
3. Запусти job с параметрами по умолчанию — обе стадии (`Verify`, `Gate`)
   должны быть зелёными.
4. Когда появится артефакт агента (например, `out/br.md`) — перезапусти с
   `ARTIFACT=out/br.md`: стадия `Gate` напечатает строку
   `benchmark score: <N> (min <MIN>)` и упадёт при `N < MIN`.

Вариант Б — **Jenkins нет**: тот же гейт локально через `ci/gate.sh`:

1. Ручной запуск: `bash ci/gate.sh cases/analytics-meeting 80 out/br.md`
   (без третьего аргумента — проверка только харнесса).
2. Git-хук: запиши в `.git/hooks/pre-push` (и сделай `chmod +x`):

   ```sh
   #!/usr/bin/env bash
   cd "$(git rev-parse --show-toplevel)"
   bash ci/gate.sh cases/analytics-meeting 80
   ```

3. Либо по расписанию (cron/systemd-таймер), с записью вывода в лог —
   строка `benchmark score:` стабильна, по ней удобно следить за трендом.

Доложи: какой вариант выбран, чем закончился первый запуск гейта.

## Шаг 5. Переключиться на боевые системы (когда они известны)

1. Моки заменяются на реальные системы **только** env-переменными —
   код серверов менять не обязательно: `TRACKER_URL`, `QUALITY_URL`,
   `FORGE_URL`, `TMS_URL` (корпоративный трекер, анализатор качества,
   git-платформа, TMS).
2. Реальным системам нужна авторизация: в каждом `mcp/*_mcp.py` HTTP-запросы
   идут через **одно место** (call-site `urllib` в функции-обёртке) — добавь
   там заголовок (`Authorization: Bearer ...` или корпоративный аналог),
   токен бери из env-переменной, не хардкодь.
3. Обнови env-блоки в конфиге CLI и в Jenkins-job (токены — в Jenkins
   credentials, не в Jenkinsfile).
4. Проверь тем же сырым пайпом из шага 3, что `tools/list` и один
   read-only вызов работают против боевой системы.
5. Доложи: какие URL подключены, где лежит токен, результат smoke-вызова.

## Шаг 6. Definition of Done и отчёт оператору

Чек-лист (отметь каждый пункт):

- [ ] код кита получен, `git log -1` показывает актуальный коммит;
- [ ] `bash scripts/verify.sh` → `RESULT: PASS`;
- [ ] все 4 MCP-сервера зарегистрированы в CLI и отвечают на `tools/list`;
- [ ] CLI успешно вызвал хотя бы один инструмент (например, `list_issues`);
- [ ] CI-гейт работает: Jenkins-job зелёный ЛИБО `ci/gate.sh` отработал
      локально/в хуке;
- [ ] понятно, где переключать `*_URL` и добавлять auth для боевых систем
      (даже если сами системы ещё не известны).

Итоговый отчёт оператору: по одному пункту чек-листа со статусом
(готово / заблокировано + причина), версия Python, коммит кита, строка
`benchmark score:` последнего запуска гейта (если артефакт уже есть) и
список всего, что потребовало отклонения от инструкции.

## Когда объявлен новый кейс

На хакатоне под свежий кейс не пишется новый харнесс — он скаффолдится
готовым `scripts/new-case.sh` (покрыт тестом `scripts/tests/test_new_case.py`):

1. `bash scripts/new-case.sh <slug> --mode rubric|findings|selection` —
   создаёт `cases/<slug>/` с `benchmark.py` нужного типа и файлами-плейсхолдерами
   (режимы соответствуют трём трекам: rubric = разделы+факты как в
   analytics-meeting, findings = precision/recall как в dev-techdebt,
   selection = recall/efficiency как в testing-regression).
2. Заполни плейсхолдеры данными кейса: вход (стенограмма / diff / код),
   эталонный артефакт, `rubric.json` или `expected-*.json`.
3. Проверь харнесс: `bash ci/gate.sh cases/<slug> <порог>` (без артефакта —
   self-test должен пройти).
4. Гейть артефакт агента: `bash ci/gate.sh cases/<slug> <порог> out/<артефакт>`
   — или тот же кейс через Jenkins-job, поменяв параметр `CASE_DIR`.

Порог подбирай в шкале бенчмарка: 0–100 для rubric-кейсов, 0–1 для
findings/selection.
